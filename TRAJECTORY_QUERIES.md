# Trajectory queries

Run from this project directory with `npm run dev`. Production verification: `npm test`, `npm run typecheck`, `npm run build`, then `npm start`.

Scene Copilot keeps the existing GPT-4o-mini integration. Set OPENAI_API_KEY in the existing local environment configuration for live interpretation. No new dependencies or separate services are needed. No generated code is executed.

Supported tools calculate zone occupancy duration, peak sampled-frame tracker-output count, and legacy entry-origin counts. Duration queries must specify total observed time or longest observed sequence; an ambiguous question asks for clarification, and a short follow-up such as “in total” resolves it. History is limited to eight alternating user/assistant messages, with 500/4000 character limits. It carries conversation text only, never authoritative evidence or system instructions.

Examples:
- How many people stayed in the tunnel for more than five seconds? Then reply: in total.
- How many track IDs spent more than five seconds in TUNNEL in one observed sequence?
- What was the peak visible count?

The raw JSONL remains on the server. Files are read and fully validated once per server process, with a cached successful promise. Failures clear the cache and return an explicit error. A new deployment/process is required to use changed static data. The Next.js /api/ask file trace includes trajectories.jsonl, trajectory_metadata.json, and results-2.json. Keep those existing exports available when preparing deployment; query_results.json is a regression reference only, never loaded by the production engine.

The engine validates frame/observation timestamps and indices, duplicate IDs, person class, bounding boxes and estimated feet, inclusive overlapping zone membership, metadata counts, and independently reconstructs the legacy movement filter and first-appearance origins. Dwell queries include every raw ID. Gaps and outside observations break intervals; singletons add zero. Total duration sums consecutive exported timestamp differences. Longest duration measures an interval's elapsed time. Comparisons are exact floating-point gt/gte against the exported seconds, without display rounding.

Evidence is returned as structured JSON and shown in collapsed, scrollable details, with per-track intervals nested inside. It includes validated parameters, counts, IDs, source frames, nominal times, provenance and limitations. The language model selects a restricted operation; application validation controls execution and deterministic prose explains the computed result. Model interpretation can still be wrong. Prompts and passing examples do not guarantee hallucination-free answers.

Entry origins retain results-2.json's meaning: filtered IDs assigned by first appearance using legacy integer centers. ALREADY PRESENT covers first sightings in the first 20 processed frames. These are not verified boundary crossings. Foot-based membership may differ from center-based entry logic. Track IDs are not guaranteed unique people. Repeated observations are not distinct events. Distances are pixels, not meters. Times are nominal playback times, not camera timestamps. An observed sequence does not prove uninterrupted presence between samples. No detection-accuracy validation, physical-safety validation, open-vocabulary detection, collision prediction, or validated uncertainty model is provided.

Tests use synthetic gaps, re-entry, singletons, exact thresholds, overlaps, boundaries, stationary unfiltered tracks, peak ties, malformed queries/data, missing files, bounded history and mocked tool dispatch. The real-export test independently computes the requested regressions and checks every supplied tunnel interval against query_results.json. Live LLM behavior is checked separately when credentials are configured; it is not part of the repeatable offline test suite. The HTTP rate limit remains eight requests per minute per client, in process memory.

Successful query responses also include a server-signed, answer-bound query context receipt, valid for one hour. The client includes it only with that assistant message in subsequent bounded history. The server verifies the signature, expiry, answer binding and query parameters against metadata before reusing it. Explicit follow-up edits preserve unspecified dwell parameters and override mode, threshold, comparison or zone when requested. Only the immediately preceding successful query response can supply this context; unrelated responses and errors clear it. Receipts are stripped before messages are sent to OpenAI. For text-only browser sessions, the server can recover only its exact canonical dwell answer: it validates the parsed query against metadata, reruns it, and requires the entire answer to match the recomputed result before inheriting parameters. Arbitrary assistant prose or inconsistent counts cannot supply context. Restarting with a different API key invalidates old receipts.
